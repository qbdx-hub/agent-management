| 学生回答 问题情况 | 童倍： 工作流采用"一张主表 + 两张子表"的三表结构存储：workflow 表保存名称、描述、状态等元信息；workflow_node 表逐行存节点（node_id、type、label、agent_id、位置坐标、config JSON）；workflow_edge 表逐行存连线（source、target、condition JSON）。节点 type 分为 start/agent/tool/condition/approval/end 六种；条件连线的 condition 字段存 {op, value} 结构（contains/not_contains/always），用于条件分支。 前端使用 Vue Flow 库渲染画布，保存时把画布上的节点和连线整体提交给后端，由后端拆解写入两张子表。运行时，后端先创建一条 workflow_run 运行记录，然后异步执行：从 start 节点出发沿连线遍历（最多 100 步，并用已访问集合防止环状连线导致死循环）；agent 节点取出绑定的 Agent 真实调用大模型并按模型单价计费；tool 节点真实发起 HTTP 请求；condition 节点用上一节点的输出评估各条出边的条件，命中哪条走哪条，都不命中走默认分支；approval 节点会生成一条审批单并把运行置为 waiting_approval 暂停，审批通过后从该节点继续执行、拒绝则终止运行。每个节点执行完都把状态、输出、耗时写回 workflow_run 的节点结果列表，前端每 2 秒轮询运行详情接口渲染执行时间线，待审批也会同步出现在安全中心的审批列表里。  施庆康： 监控模块主要通过两种方式获取 Agent 运行状态。第一种是实时状态查询：从 agent 表读取 status 字段（active/idle/error 等），从 session 表和 execution_step 表关联查询最近的执行记录，包括执行时长、成功失败状态、错误信息等，在前端用 ECharts 渲染成趋势图表。第二种是告警机制：alert_rule 表中预配置了告警规则，比如"某 Agent 错误率连续 5 分钟超过 10%"或"Token 消耗超过预算 80%"，后端定时任务轮询触发条件，命中后写入 alert_record 表并通知相关人员。 成本管理方面，Token 消耗的统计口径是：每次 Agent 调用大模型时，后端记录本次请求的 input_tokens（输入 Token 数）和 output_tokens（输出 Token 数），根据 model_pricing 表中该模型的单价（输入单价、输出单价）计算费用，写入 cost_record 表。cost_record 表关联了 agent_id、model、tokens、cost 等字段，支持按 Agent、按模型、按时间维度聚合统计。budget 表配置每个工作空间或 Agent 的月度预算上限，当累计消耗接近阈值时触发告警。  赵梓涵： 知识库的 RAG 检索流程分为离线入库和在线检索两个阶段。离线入库阶段：用户上传文档后，系统将文档存入 document 表，同时对文档进行分块处理（按段落或固定长度切分），调用向量化接口将每个文本块转为向量 embedding，向量连同原文存入向量存储。在线检索阶段：当 Agent 配置了知识库绑定时，用户提问后，系统将查询文本同样向量化，与知识库中的文档向量做余弦相似度匹配，取 Top-K（默认 5）最相关的文本块，拼接为上下文注入到 Agent 的 System Prompt 中，让大模型基于这些资料生成回答。 安全审计模块通过三层机制保证可追溯性。第一层是操作日志：audit_log 表记录所有敏感操作（创建/删除 Agent、修改权限、绑定工具等），包含 operator_id（操作人）、action（操作类型）、target_type、target_id、detail（操作详情 JSON）、created_at，支持按时间、人员、操作类型查询。第二层是审批流程：对高风险操作（如删除生产环境 Agent、修改 API Key），approval_rule 表定义哪些操作需要审批，approval 表记录审批申请和审批结果，操作前必须经过有权限的人审批通过。第三层是 API Key 管理：api_key 表加密存储模型供应商密钥，通过时不再明文展示，仅显示脱敏后的前几位，防止密钥泄露。  唐建睿： 需求分析阶段分三步进行。第一步是竞品调研：我们调研了 Dify、Coze、FastGPT、LangFlow 等市面上主流的 AI Agent 管理平台，分析了它们的功能覆盖范围、技术架构和不足之处，发现现有产品大多面向个人开发者，缺少团队协作、成本管控、安全治理等企业级能力。第二步是用户画像分析：我们定义了四类目标用户——Agent 开发者（创建调试单个 Agent）、编排工程师（设计多 Agent 协作流程）、团队管理者（看用量管权限）、平台管理员（管模型和全局安全），每类用户的核心需求对应系统的功能模块。第三步是功能边界定义：通过 MoSCoW 方法（Must/Should/Could/Won't）对功能排优先级，Must 级别的功能（Agent CRUD、工具管理、编排、基础监控）纳入第一期，Should 级别（成本管理、知识库 RAG）也纳入，Could 级别（链路追踪、灰度发布）留到后续迭代。 PRD 文档在团队协作中起到了三个作用：一是统一认知，4 个人对系统功能的理解保持一致，避免各做各的；二是接口契约，PRD 中明确了每个模块的输入输出和 API 设计，前后端可以并行开发；三是验收依据，开发完成后对照 PRD 验收功能是否达标，避免功能遗漏或偏离需求。我在维护 PRD
