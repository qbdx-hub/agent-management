### 1.2 测试策略

- **真实调用**：所有用例均为对运行中后端的真实 HTTP 请求（非 Mock），响应逐条存档（共 117 条原始执行记录，含参数修正复测）。
- **正反结合**：除正常流外，覆盖错误密码登录、重复注册、无 Token 访问、非法状态值、参数缺失等异常分支。
- **数据自清理**：测试创建的工作空间/Agent/工具/会话/知识库/工作流/预算/角色/API Key 在用例内创建并删除，不污染种子数据。
- **自证闭环**：审计日志模块验证的正是本次测试自身产生的操作记录（角色删除 `role.delete` 被完整落库）。
- **口径说明**：每个模块的登录调用为前置准备，不计入用例；首测因测试输入问题（参数遗漏/级联空 ID）失败的用例，修正输入后复测，取复测结果计入；业务错误约定为 HTTP 200 + 业务码（`code != 0`），认证缺失为 HTTP 401，与后端统一响应封装一致。

## 五、缺陷与改进项

### 🐞 BUG-01（严重级：功能不可用）API Key 子模块全部接口 500

**现象**：`POST/GET /security/api-keys`、`PUT .../status`、`DELETE .../{id}` 均返回 `code=500 系统繁忙`。

**根因分析**（三重问题叠加）：

1. **schema.sql 重复建表**：`api_key` 在 `docs/database-schema.sql` 中被定义了**两次**——第 546 行「API Key表」（workspace_id / provider / key_prefix / scopes / expires_at / created_by）与第 744 行「API密钥表」（user_id / mask / key_hash CHAR(64)）。因 `CREATE TABLE IF NOT EXISTS`，第二版被**静默跳过**，实际生效的是第一版。
2. **实体类与实际表不匹配**：`ApiKey.java` 按 744 行第二版设计（字段 `userId`、`mask`），而真实表没有 `user_id`、`mask` 列。
3. **运行时必然失败**：MyBatis-Plus 生成 `INSERT INTO api_key (user_id, name, key_hash, mask, ...)` → `Unknown column 'user_id' in 'field list'` → 全局异常处理器兜底为 code=500。

**影响面**：API Key 的创建/列表/启停/删除 4 个接口全部不可用；该功能（个人密钥管理，明文仅返回一次的安全设计）从未真正跑通。

**修复建议**（二选一，建议 A）：

- **方案 A（保留代码设计）**：删除 schema.sql 第 546~564 行的旧版定义，保留 744 行版本（`user_id`/`mask`/`uk_key_hash`），与 `ApiKey.java`、`ApiKeyServiceImpl`（`sk-my-` 前缀 + SHA-256 + 掩码）对齐。
- **方案 B（保留表结构）**：改造 `ApiKey.java`（workspaceId/provider/keyPrefix/scopes/expiresAt/createdBy）并重写 Service 逻辑。

同时建议：`CREATE TABLE IF NOT EXISTS` 重复表名应在 CI 中做校验（同名建表脚本静默失效是本 bug 长期未被发现的原因）。

### 🔧 IMP-01（易用性）监控接口缺必填参数时返回 500 而非 400

`MonitorController` 的 `period`、`enabled` 等为必填 `@RequestParam` 且无 `defaultValue`，缺失时抛 `MissingServletRequestParameterException`，被兜底为 `code=500 系统繁忙`。建议：为 period 类参数设 `defaultValue="7d"`（与 CostController 对齐），并在全局异常处理中将该异常映射为 `code=400` 与明确字段提示。

### 🔧 IMP-02（数据质量）上传文档分块内容带 UTF-8 BOM

`document_chunk.content` 开头残留 `﻿`（BOM），会出现在检索命中内容中。建议解析阶段 strip BOM。

### 🔧 IMP-03（提示优化）工具测试接口入参校验提示

`POST /tools/{id}/test` 的 `parameters` 为 `Map` 结构，误传字符串时报 `1001 请求体格式错误`，未指明字段；建议校验消息中给出字段名与期望结构示例。

## 六、环境受限项（非缺陷）

以下能力的**接口链路均已验证通过**，但端到端 AI 效果依赖真实 LLM API Key（`agent.ai_base_url/ai_api_key` 当前为空），本环境无法验证：

| 受限项 | 已验证部分 | 受限部分 |
|--------|-----------|----------|
| SSE 真实 LLM 对话 | SSE 通道、thinking→content 事件序列、降级文案 | 模型真实生成内容、多轮上下文质量 |
| RAG 向量语义检索 | 上传/解析/分块/文本命中 | embedding 生成与向量相似度排序 |
| 工作流 Agent 节点执行 | 画布持久化、运行引擎、失败状态与节点结果记录 | Agent 节点真实调用 LLM 产出 |

**补充验证建议**：配置任一 OpenAI 兼容 API Key 后，重点回归上述三项；V10 上下文压缩（context_summary）同样依赖 LLM，建议一并验证。
